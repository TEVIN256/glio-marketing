# Decisions

One short record per decision: context, decision, consequence. Newest last.

## ADR-001 Start with TikTok, one channel at a time

**Context.** Glio will cover TikTok, Snapchat, Meta, Google Ads (incl. YouTube) and Google Business Profile. TikTok is the founding agency's biggest channel and has a medium-difficulty API review (~1–2 weeks).
**Decision.** Build and prove the full flow on TikTok first. Add Snapchat, then Meta, then Google, then Business Profile, each only after the previous one passes its real-data tests.
**Consequence.** Every platform sits behind one `Connector` interface so later channels don't change the core. Meta Business Verification starts early in the background because WhatsApp depends on it.

## ADR-002 Supabase (Postgres + Auth + RLS) as the system of record

**Context.** We need Postgres, email/magic-link login with 2FA for owners, and tenancy enforced by the database. The founder already runs Supabase for another product.
**Decision.** Use one dedicated Supabase project for Glio. Tenancy is enforced with row-level security on every table, using `auth.uid()` and membership helpers (`is_member`, `has_ws_role`, `can_see_client`).
**Consequence.** Schema lives in `supabase/migrations/` as plain, reviewed SQL. Tests run the same migrations against plain Postgres using a small shim of Supabase's `auth` schema (`packages/db/test/supabase-shim.sql`), so CI never touches the real project.

## ADR-003 One engine for businesses and agencies

**Context.** Glio serves business owners directly (self-serve) and agencies managing many clients.
**Decision.** A `workspace` has `kind = 'business' | 'agency'`. A business workspace is an agency with one client (created automatically). Roles: owner, manager, analyst, client_viewer.
**Consequence.** No separate code path per customer type; screens differ by `kind` and role. Inviting an agency into a business workspace is a later feature (guest membership) and fits this model.

## ADR-004 Approvals and audit log exist from day one

**Context.** Glio will change live ad spend. Trust and liability require that nothing executes without approval, and that every action is traceable.
**Decision.** `approval_requests` and an append-only `audit_log` ship in the first migration. Updates, deletes and truncates on `audit_log` are blocked by trigger for every role, including the server.
**Consequence.** Write actions in later stages plug into an existing approval path. Purging old audit entries for retention will need a dedicated, logged procedure.

## ADR-005 Platform credentials are server-only

**Context.** TikTok and other platform tokens grant control of real ad accounts.
**Decision.** Tokens are stored in a secret store; the database keeps only a reference in `ad_account_credentials`, a table with RLS enabled, no policies and no grants to signed-in users.
**Consequence.** Only server code using the service role can resolve credentials. Tokens are never logged and never sent to the AI.

## ADR-006 Glio never generates images or video, and never holds ad money

**Context.** Platforms already give creative generation away; handling ad spend would make Glio a payments business.
**Decision.** Glio writes text only (copy, plans, summaries). Creatives come from the business. Ad spend is charged by the platform to the business's own card.
**Consequence.** No creative-generation dependencies. Glio's own subscription billing is separate and must be ZATCA-compliant.

## ADR-007 Explicit grants only; Supabase's automatic table exposure stays off

**Context.** Supabase can grant API roles access to every new table automatically. That makes access depend on a dashboard setting instead of reviewed SQL.
**Decision.** Projects are created with "Automatically expose new tables" off and "Enable automatic RLS" on. Every grant Glio relies on, including for the server role, is written in a migration. The test shim mirrors this (no default privileges).
**Consequence.** A table someone forgets to grant fails loudly in tests instead of being silently exposed.

## ADR-008 Raw payloads are the evidence; metrics are derived and upserted

**Context.** Every number Glio shows must trace to what the platform returned, and re-running a sync must never duplicate or drift.
**Decision.** Each API page is stored unchanged in `raw_platform_payloads` with a SHA-256 of its canonical JSON (keys sorted). The fingerprint excludes fields that change on every call without the data changing (TikTok's `request_id`), so identical data is stored once per account. Raw rows are immutable; they disappear only through the ad-account cascade (account or workspace deletion). `metric_daily` rows are upserted on `(ad_account_id, level, entity_id, date)` and point at their raw payload; unchanged rows are not rewritten. Metrics are written in one transaction only after every page succeeded. Money is converted to minor units exactly and a value needing rounding fails the sync. `NULL` means "not provided by platform".
**Consequence.** Re-runs are provably idempotent (M2 gate). Restated data (late conversions) updates only the affected rows, and the older raw version remains as history. Raw storage grows only when data actually changes.

## ADR-009 TikTok connector built before API access, details isolated

**Context.** TikTok API access isn't approved yet, and the API details used come from memory of v1.3 while TikTok now also documents v2.0.
**Decision.** Every TikTok-specific detail (URLs, parameter and metric names, limits, error codes) lives in `packages/connectors/src/tiktok/api.ts`, marked `TODO(verify)`. The connector is tested against synthetic fixtures through an injected HTTP layer. Retries happen only for errors the connector marks transient (HTTP 429/5xx for now).
**Consequence.** Switching to the verified API is a change to one file and the fixtures. No live TikTok call has been made yet; nothing here is proven against the real API.

## ADR-010 Platform tokens live in a secret store, not the database

**Context.** The database stores only `secret_ref`.
**Decision.** A `SecretStore` interface resolves refs to tokens. Only an in-memory implementation exists, for tests. The production store (Supabase Vault or a KMS-backed store) is chosen before the first real TikTok account is connected.
**Consequence.** Tokens never reach tables, logs or sync error messages (tested); the production store is an open item.

## ADR-011 Reconciliation: our stored totals vs the platform's own totals

**Context.** Reported numbers must tie to platform totals; drift must be visible, not discovered by a client.
**Decision.** After a successful sync, `reconcile()` asks the platform for account-level totals over the sync run's dates (split and summed if longer than one request allows), archives that response, and compares it with the sum of the stored campaign rows: spend (minor units), impressions, clicks, conversions (scaled by 10^4). Drift = |ours − theirs| / theirs in parts per million, decided with exact integer arithmetic; flagged when strictly greater than the threshold (default 5,000 ppm = 0.5%). Missing values are "not comparable", never zero; "platform reports 0 / no activity but Glio stored some" is always flagged. One row per metric goes to the append-only `reconciliation_checks`, and a structured log event is emitted (`warn` on drift, `error` on failure, never credentials). `reconciliation_latest` (security_invoker view) gives the UI the newest result per metric.
**Consequence.** Every check is provable after the fact: both numbers, the threshold used and the platform response are stored. Comparing campaign-level sums to account totals can legitimately differ (e.g. deleted campaigns, late attribution); that is what the flag is for. Thresholds per client and alerting (WhatsApp/email) come later.

## ADR-012 Reports are snapshots of figures with provenance

**Context.** We must be able to prove what a client saw on a given date, and a reviewer must be able to go from any figure to the platform response behind it.
**Decision.** A report is a list of figures (id, exact value or explicit reason it has none, English and Arabic display text, raw payload ids). Base figures are sums of `metric_daily`; derived figures (CTR, CPC, CPA) are computed from exact integers, with only their display rounded half-up and the exact numerator/denominator kept. ROAS is "not provided" until a revenue source is connected. Display formatting is our own deterministic code (no ICU), with Western or Arabic-Indic digits per report. `report_snapshots` stores the full report JSON and its SHA-256; snapshots and commentary are permanent records.
**Consequence.** Any stored report can be re-verified later against the raw payloads it cites (the M5 gate does exactly that). Changing formatting or metrics later creates different snapshots; old ones stay as they were shown.

## ADR-013 AI commentary: figures in, validated text out, template as the floor

**Context.** The AI must never produce or alter a number, and must say when data is missing.
**Decision.** Claude (`claude-opus-5-5`, structured JSON output with Arabic and English fields, effort `medium`) receives only the period, channels and figures with their display text: no raw payloads, credentials or client names. Every number in its output (after normalising Arabic-Indic digits, Arabic separators and bidi marks) must appear exactly in a figure display or the period dates; numbers written as words are rejected. On failure: one retry with a stricter instruction naming the offending numbers, then a deterministic template. Missing metrics are always stated by a code-generated sentence, not left to the model. Every attempt (including rejected output and errors), the exact input and its hash, the prompt version and the prompt's hash are stored in `ai_commentary`. Server-side refusal fallbacks are not enabled: a refusal falls through to the retry and then the template.
**Consequence.** The worst case is a plainer, template-written summary, never a wrong number. The validator can't judge whether a correct number is described correctly (e.g. attributing clicks to the wrong channel); the prompt and review address that, not the validator. Sending figures to the Claude API means aggregated metrics leave the Kingdom (see COMPLIANCE.md).

## ADR-014 Web app: Next.js server rendering, reads as the user, writes behind a permission check

**Context.** The first usable screens: sign-up/login, workspaces, clients, the client dashboard, stored reports, and figure provenance, Arabic-first.
**Decision.** Next.js 16 App Router, every page server-rendered with `<html dir="rtl" lang="ar">` (English via a cookie), styles using only logical CSS properties. Supabase Auth (email + password, email confirmation) through `@supabase/ssr`; `proxy.ts` refreshes the session and sends signed-out visitors to /login. **All page reads use the Supabase client as the signed-in user**, so row-level security decides what is shown. Server-only writes (report snapshots, demo syncs) use a direct Postgres connection (`DATABASE_URL`, server-only) and are allowed only after `clientAccess()` confirms the user's role under RLS. Numbers and dates inside text are wrapped in direction-isolated spans so Arabic layout can't reorder them. Shared packages import their own files with `.ts` extensions (`moduleResolution: Bundler`) so the same source runs in Vitest and in Next's bundler.
**Consequence.** A bug in a page can't show another workspace's data, because the database refuses it. The server-privileged connection is the sensitive part: every new use must be preceded by a permission check. 2FA for owners, magic links, the client portal's white-label branding and expiring share links are still to come.

## ADR-015 Company website and the app share one domain and one deployment

**Context.** TikTok's developer registration (and later Meta, Snapchat, Google) needs a company website on the company domain with a privacy policy and terms, and the OAuth redirect URL must be on that domain. The owner's company is Sutoor AlMustaqbaliyya Agency for Commercial Services, trade name Glio Agency, domain `glioagency.org` (previously a Shopify store).
**Decision.** The same Next.js app serves the public website and the product. `/` is the public home page; `/privacy` and `/terms` are public; the signed-in workspace list moved from `/` to `/app`. `isPublicPath()` in `proxy.ts` is the single list of public paths (exact or followed by `/`, so `/privacy-x` is not public). Company facts live in `COMPANY` in `lib/site.ts`; a null field is not shown. **The public brand is "Glio" only**: by the owner's choice the legal entity name is not shown anywhere on the site (kept in `COMPANY` for platform applications), contact is email only (no phone), and the CR number is shown (tested). Site text is Arabic-first with English, same structure in both (tested). DNS for `glioagency.org` moved to Cloudflare (DNS-only records, no proxy) on 2026-11-21; the registration stays at Shopify until it is transferred.
**Consequence.** One deployment, one certificate, one cookie domain; the TikTok redirect URL can be `https://glioagency.org/...`. Policy text is written to match what is built today and must change when the product does (new providers, data, retention). It has not had a legal review. Not naming the legal entity on the privacy policy may fall short of PDPL's requirement to identify the controller, and platform reviewers may expect the site to match the registered company; revisit if either is raised.

**Update (2026-11-21): one blended site.** glioagency.org already had a Shopify agency site ("GLIO": services, free audit, waitlist). The owner chose to blend it with the platform: the public site now sells three agency services (paid ads management, tracking + data setup, SEO + visibility; store building dropped) alongside the Glio platform, in the old site's dark blue style. Pages are split into route groups, `app/(site)` (dark public site with its own header/footer) and `app/(app)` (light product UI); URLs are unchanged. The main call to action is "Ask for a demo" as an email to info@glioagency.org with a prefilled subject and body: no form and no new table until we decide where leads live (a lead table would need a migration reviewed first, and has no workspace). The Shopify site stays on glioagency.org until the owner approves the new one; then the domain moves to Vercel in one step.

## ADR-016 Connecting TikTok: OAuth state cookie, tokens in Supabase Vault

**Context.** Advertisers connect their own TikTok ad accounts. The access token must never reach the browser, logs, our tables or the AI, and tenancy rules must hold.
**Decision.** "Connect TikTok" (owners/managers, checked under RLS) creates a random state, keeps it with the workspace and client in a 10-minute httpOnly, SameSite=Lax cookie scoped to `/integrations/tiktok`, and sends the user to TikTok's authorization page. The callback (`/integrations/tiktok/callback`, a route handler) requires the returned state to equal the cookie's (constant-time compare), re-checks the user's role, exchanges the auth code server-side, lists the advertisers the token can use (rejecting advertiser IDs that arrive as imprecise JSON numbers), and calls `connectAdAccounts()`. That stores the token in **Supabase Vault** (`VaultSecretStore`: `vault.create_secret` / `vault.decrypted_secrets`, via the server's database role; ref `vault:glio/tiktok/<uuid>`), attaches each account to the client (`status = active`), never moves an account already attached to another client in the workspace, audits every connection (`ad_account.connected`), stores nothing if nothing can connect, and deletes a replaced token once nothing references it. "Sync TikTok data" runs the existing sync and reconciliation for the client's connected accounts. No migration was needed.
**Consequence.** Tokens are encrypted at rest by Supabase and readable only with the server's database credentials (DATABASE_URL), which therefore protect both data and tokens. Vault lives in the same Frankfurt project (data residency question unchanged, see COMPLIANCE.md). Tests use a plain-table stand-in for the Vault interface (no encryption), so Vault itself must be checked in the real project (RUNBOOK). The TikTok endpoints remain `TODO(verify)` until the first real connection.

## ADR-017 Emailed reports: snapshot first, one email per recipient, logged, sent once

**Context.** Clients should receive their report by email on a schedule, in Arabic first, without anyone being able to claim the email said something the dashboard didn't.
**Decision.** Per-client `report_schedules` (off / weekly on a chosen ISO weekday covering the previous 7 days / monthly on the 1st covering the previous month; language; up to 20 recipients, validated in the app and by a database check). A delivery first creates a normal report snapshot (permanent, same figures and validated commentary as the dashboard), then renders the email ONLY from it (`renderReportEmail`: no number is computed there; everything HTML-escaped; Arabic right-to-left with isolated numbers) and sends one email per recipient (recipients never see each other) through Resend's HTTP API (no SDK; `Idempotency-Key` per snapshot and recipient). Every attempt goes to the permanent `report_deliveries` log (server-only writes); a unique index makes a scheduled report "sent" at most once per client, period and recipient. A daily Vercel Cron (`/api/cron/reports`, 05:00 UTC = 08:00 Riyadh, protected by `CRON_SECRET`) refreshes the client's TikTok data, then sends what is due; missed or failed sends are retried for two more days. A failed refresh sends nothing and is logged. Owners and managers edit schedules (RLS) and can "send now" for the chosen period.
**Consequence.** What a client received can be shown exactly (snapshot + delivery row). Recipient addresses are personal data held per client (see COMPLIANCE.md). The email's "open in GLIO" link only works for people with a GLIO account; expiring share links for external recipients are not built yet. Vercel Hobby runs crons once a day and a function for at most 60 s, which bounds how many clients one run can serve.


## ADR-018 App redesign: navy sidebar, live dashboard computed like reports

**Context.** The product pages were plain prototypes; the owner wanted a finished look matching the website. Chosen direction: navy sidebar + light content area.
**Decision.** Route groups: `(app)` gets a navy sidebar (workspaces and their clients, read under RLS; language; sign out) and a light content area; sign-in moved to `(auth)` with a brand panel. The client dashboard has date presets (7/14/30/90 days, this month, last month, ending yesterday in Asia/Riyadh) and a custom range in one row; KPI tiles with the exact change vs the previous period of equal length (bigint rationals, rounded only for display; "good/bad" per metric, always shown with an arrow and text, never colour alone; spend is neutral); a single-series daily chart (SVG, no chart library, GLIO blue validated for contrast, hover crosshair + tooltip with the exact value, keyboard arrows, days without stored data drawn as gaps not zeros, a table view); and a campaigns table with share of spend. These live numbers are computed from `metric_daily` with the SAME `loadChannelTotals` + `buildReport` code as reports, after the RLS check, so a dashboard and a report for the same period agree. Report snapshots remain the permanent record (print/PDF from the browser).
**Consequence.** No new dependencies. The dashboard reads with the server connection after `clientAccess()`; any new section must keep that order. A design preview (local only, not committed) renders the same components against a synthetic local database for visual review.

## ADR-019 Approvals: one executor, guardrails, before/after state, undo

**Context.** Firm rule 3: no platform write without approval, through one executor that enforces budget caps, saves the before-state and supports undo.
**Decision.** Owners, managers and analysts propose campaign changes (pause, turn on, daily budget) as `approval_requests` rows under RLS (pending, as themselves, no execution fields). Users can no longer update requests: owners/managers decide only through `decide_approval()` (SECURITY DEFINER: role, visibility, status and expiry checked; audited). "Approve and apply" then calls `executeApproval()`, the ONLY code that writes to a platform: it claims the request (approved -> executing under a row lock, so it can't run twice), reads the campaign's current state from the platform, enforces `client_guardrails` (maximum daily budget; maximum increase per change, default 50%), writes, reads the after-state, stores both, and audits success or failure. Undo (owners/managers, 30 days) creates a new approved request restoring the stored before-state (the increase cap does not apply to a restore; the maximum budget does), locked against double clicks, and marks the original `undone`. The demo account uses a writer that sends nothing and carries state from the last executed change. TikTok campaign endpoints are `TODO(verify)` like the reporting ones.
**Consequence.** Every platform change has a who/why/when/before/after record and an undo path. AI agents and rules will create requests through the same table (`requested_by_agent`); nothing they propose runs without a human decision. Execution happens in the request that approves it (no queue yet); a long platform outage leaves the request `failed` with its error, to be proposed again.

## ADR-020 GLIO suggestions: deterministic rules that only propose

**Context.** The "AI agents" promise: GLIO should notice what needs doing and prepare it, while firm rule 3 (no action without approval) and rule 2 (numbers are never invented) hold.
**Decision.** Rules v1 (`suggestForClient`, agent `glio-rules/v1`) read the last 7 complete days of stored campaign metrics and insert `approval_requests` with `requested_by_agent`, never executing. Three rules: pause on spend with zero conversions; cut the daily budget 20% on high cost per conversion vs the client's; raise it 20% (capped by the client's safety limits, and marked when limited) on low cost per conversion. Comparisons are exact integer cross-multiplications; campaigns with any day missing spend or conversions are not judged. The current state (running? daily budget?) is read from the platform through the same `campaignAccess()` the executor uses. Every number goes into `payload.evidence`; the reason is rendered from it in Arabic or English (an English copy is kept in `reason`). No repeat while a request is open, or for 7 days after a decision; 72-hour expiry; every suggestion audited (`approval.suggested`, actor `agent`). Runs daily inside the single daily cron (Vercel Hobby limits cron jobs; renamed `/api/cron/reports` -> `/api/cron/daily`: refresh, suggest, report) and on demand from the Approvals page. Demo data gained campaigns C/D/E to exercise the rules.
**Consequence.** Suggestions are explainable and checkable; an LLM may later phrase or prioritise them but never supply their numbers. The thresholds are global defaults for now (per-client settings later). Everything runs in one 60-second function on the Hobby plan, which bounds how many clients one run can serve.

## ADR-021 Approval notifications by email

**Context.** Suggestions and proposals only help if an approver sees them the same day.
**Decision.** `notifyPendingApprovals()` (reports package) emails each owner and manager of a workspace separately about pending, unexpired requests not yet announced, then sets `approval_requests.notified_at` (migration 0008) so each request is announced once. It runs after "Check for suggestions now" and after a person proposes a change (skipping that person), and in the daily job after the suggestion step (no exclusion). If every send fails the requests stay unannounced and are retried; if nobody needs telling they are marked so they don't arrive later out of context. People opt out per workspace (`notification_settings.approvals_email`, own row only, RLS). The email is rendered by the web app from the same plain-language descriptions as the Approvals page, Arabic first then English, numbers isolated for right-to-left, everything escaped; Resend idempotency key per batch and person. Users cannot set `notified_at` when proposing (insert policy). Audited as `approval.notified`.
**Consequence.** Approvers learn about waiting changes without checking the page. No email is sent without `RESEND_API_KEY`; requests then wait unannounced until it is set. WhatsApp can reuse the same "unannounced" marker later.

## ADR-022 Team invitations

**Context.** Agencies need their team (managers, analysts) and their clients (client viewers) inside GLIO; there was no way to add anyone.
**Decision.** Owners invite an email as manager, analyst or client_viewer (tied to one client) from the workspace's Team page. The link carries a random 256-bit secret; only its SHA-256 is stored (`invitations`, migration 0009), valid 7 days, one open invite per workspace and email (a new one revokes the old). The link is emailed (Arabic first, then English) and shown once to the owner via a short-lived httpOnly cookie, never in URLs or logs. Joining goes only through `accept_invitation()` (SECURITY DEFINER): valid, unexpired, unrevoked, and the signed-in (confirmed) email must equal the invited one, so a forwarded link is useless; it never changes an existing member's role; audited (`member.joined`). `invitation_preview()` lets the invite page show what it is for before joining, masking the invited email for other accounts. Owners can only revoke invites (column grant). Members' emails are read on the server only for the members RLS already returned. Sign-in/sign-up return to the invite page: `next` for sign-in, a one-day httpOnly cookie for sign-up (keeps Supabase's confirmation URL on its allow-list); `safeNext()` allows only internal paths.
**Consequence.** No owner-to-owner invites or ownership transfer yet; an owner can't change their own role (unchanged rule). Invites work without email configured (the owner shares the link).

## ADR-023 Per-client suggestion settings

**Context.** One global set of thresholds doesn't fit every client (budgets and conversion costs differ by orders of magnitude).
**Decision.** `suggestion_settings` (migration 0010), one row per client: on/off, pause spend with no conversions (major units of the account currency), high/low cost-per-conversion percentages vs the client's average, minimum conversions for cut/raise, and the budget step. No row = the rules v1 defaults. Database checks bound every value; owners and managers edit (RLS), everyone who can see the client reads; saves are audited. `suggestForClient` loads the row (`loadClientRules`), returns `disabled` when off, and records the thresholds it used in each suggestion's evidence. The minimum spend before judging cost per conversion stays a global default.
**Consequence.** Agencies can tune GLIO per client without code changes; suggestions remain explainable because their evidence names the thresholds.


## ADR-024 Report share links

**Context.** Clients and their staff usually have no GLIO account, but report emails linked into GLIO, which needs sign-in.
**Decision.** `report_shares` (migration 0011): a read-only link to one report snapshot, `/s/<secret>`. The secret is 32 random bytes; only its SHA-256 is stored, and it is shown once to the person who created it (short-lived httpOnly cookie, never in a URL we log). Links expire (7, 30 or 90 days; report emails create a 30-day link, labelled `report-email`), owners/managers revoke them, and a composite foreign key ties each link to the snapshot of the same client. Users can only insert (with a clean row) and set `revoked_at`; only the server writes `view_count` / `last_viewed_at`. The public page shows the stored snapshot exactly (same figures and commentary as in GLIO), without links into GLIO, marked `noindex` and `no-referrer`. Expired, revoked and unknown links all show the same "not available" page.
**Consequence.** Anyone holding the link can read that one report until it expires or is revoked, so links are treated like the report itself. Opening a link records a count, not who opened it (no IP or device stored).

## ADR-025 Sign-in emails through Resend, with links that work in any browser

**Context.** Supabase's built-in email sender is limited to a few emails per hour and sends from a Supabase address in English only. Its default links (`?code=`, PKCE) only work in the browser where sign-up or the reset started, which caused "could not sign in" confusion.
**Decision.** Supabase Auth sends through Resend SMTP (a separate send-only key, entered only in Supabase) from `no-reply@glioagency.org`. Templates live in `supabase/templates/` (Arabic first, then English, in one email, since the person's language isn't known before sign-in) and link to `/auth/confirm?token_hash=…&type=…`. That page shows one button; pressing it calls `verifyOtp` on the server, which works in any browser and is not used up by email scanners that open links. Recovery continues to `/reset-password`; confirmation to the page remembered at sign-up or the app. `/auth/callback` stays for links already sent.
**Consequence.** Templates are pasted into the Supabase dashboard (not deployed by Vercel); `supabase/templates/` is the source and a test checks their links. Resend is listed as a provider in the privacy policy.

## ADR-026 One-click unsubscribe from report emails

**Context.** Report emails go to people outside GLIO (clients and their staff). They must be able to stop them without writing to us, and Gmail and Yahoo expect a one-click `List-Unsubscribe` for regular senders.
**Decision.** Migration 0012. Each email gets its own random link secret; only its SHA-256 is stored, on the (append-only) delivery row, so a link identifies exactly one recipient and client. The footer links to `/u/<secret>`: opening it changes nothing (email scanners open links), its button unsubscribes. The `List-Unsubscribe` header points at `/api/unsubscribe/<secret>` with `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, which unsubscribes on POST. Unsubscribes are stored per client and address in `report_unsubscribes`; every send (manual or scheduled) skips them, and a client whose recipients all unsubscribed isn't even refreshed. Team members can see the list but have no write access: only the person, with the same link, can subscribe again. Links don't expire. Approval notifications and invitations are account emails (in-app setting / one-off) and have no unsubscribe link.
**Consequence.** Re-adding an unsubscribed address to the recipients list does not restart emails; the team has to ask the person to use their link.

## ADR-027 The website names the legal entity behind GLIO

**Context.** TikTok rejected the developer profile because the company name (the legal name on the Commercial Registration) did not match the website or email domain, which showed only "GLIO". The website previously hid the legal name (owner's choice).
**Decision.** The owner chose to show it: the footer reads "GLIO, a trading name of <legal name> · CR <number>", and the about text and the privacy and terms intros name the legal entity and CR (Arabic and English). Contact stays email only. A test checks the legal name and CR appear in all four places.
**Consequence.** Platform reviews (TikTok now; Meta, Snap and Google later) can match brand, domain and legal entity; the privacy policy now identifies the controller.

## ADR-028 TikTok API details checked against the official documentation

**Context.** The TikTok connector was written from memory, with every endpoint detail marked `TODO(verify)`.
**Decision.** Checked on 2026-11-24 against TikTok's official docs and SDK (doc ids in `packages/connectors/src/tiktok/api.ts`). Confirmed: base URL, authorization and token exchange (long-term token, no refresh in v1.3), advertiser list/info, report parameters and limits, campaign get/status/update, enum values. Changed: TikTok's "-" metric value is read as "not provided" (never zero); campaign reports include deleted campaigns (`campaign_status` STATUS_ALL) so they add up to the account totals; throttling and system error codes (40016, 40100, 40133, 40202, 50000, 50002, 51305, 60001) are retryable; token errors show "connect TikTok again". Noted: status updates take at most 20 campaigns (GLIO sends one), budgets below 105% of spend or under SAR 50 a day are refused by TikTok. Confirmed on the first real account (2026-11-26): an inactive range returns one totals row of zeros, and campaign-day reports include zero rows. Still open: the advertiser/info id limit.
**Consequence.** v1.3 stays (no announced end date). TikTok's v2.0 reporting (POST, `advertiser_ids`) is the likely migration later; it lives behind the same connector interface.

## ADR-029 Data retention and client deletion

**Context.** The privacy policy only said data is kept "while the account is active", and there was no way to delete a client's data from inside GLIO.
**Decision.** (1) Owners delete a client from its page, typing its name to confirm. `deleteClientData` deletes the client row in one transaction; every table holding client data references the client with ON DELETE CASCADE (a test checks every table with a `client_id` column is empty afterwards), the append-only logs allow cascade deletes only, and the client's platform tokens are then removed from Vault when nothing else uses them. The audit log records `client.deleted` with the name and record counts, never content. (2) Migration 0013 adds `purge_expired_data()`, run daily: invitations 90 days after they close, report delivery rows (recipient emails) after 24 months. The delivery log's guard lets only that function delete old rows; the server role lost its delete grant. (3) The audit log is never deleted (firm rule); its retention period is left for legal advice. Periods are published in the privacy policy.
**Consequence.** Deletion is immediate and irreversible (no soft delete). Token revocation at TikTok, workspace deletion and user-account deletion are still manual, on request.

## ADR-030 First connection: sync right away, and say what state the client is in

**Context.** After connecting TikTok nothing was synced until someone pressed a button, and every empty page said "connect TikTok, or load demo data", even with an account connected.
**Decision.** The OAuth callback syncs the last 30 complete days (the page's default period, kind `backfill`) before redirecting, with a 60-second function limit; a failure keeps the accounts connected and is shown with its hint. The client page distinguishes four states from the accounts and their sync runs (`lib/sync-status.ts`): not connected, connected but never synced, synced with no activity in the period, and figures. Each account shows its last sync or last failure (Riyadh time). Error hints are looked up through `hintFor`, which also understands wrapped codes (`SYNC_tiktok_40105`).
**Consequence.** The first real client sees figures on the first page load after connecting. Very large accounts could make the first sync slow; if it exceeds the limit the page falls back to "never synced" with the sync button.

## ADR-031 Purchase value and return on ad spend from TikTok

**Context.** Ads Manager shows "Purchase value (website)" and "Purchase ROAS (website)" for sales accounts; GLIO showed ROAS as "Not provided by platform" because it never asked TikTok for revenue.
**Decision.** Migration 0014 adds `metric_daily.purchase_value_minor` (minor units of the account currency, exact; TikTok's `total_complete_payment_rate`, checked against TikTok's docs: a total value in the account currency, "0.00" for none, "-" when not applicable → stored as NULL, never zero). ROAS is computed, never stored: purchase value / spend, exact numerator and denominator, displayed to 2 decimals. TikTok's own `complete_payment_roas` is requested only so the raw payload keeps it for verification. Reconciliation compares purchase value with TikTok's account total when both exist; when either side lacks it, it is skipped, so accounts without website purchase tracking keep their "Matches the platform" badge. Purchase value and ROAS appear on the dashboard (tiles, campaign table), reports, the shared page, emails and the automatic summary, in one shared order (`METRIC_ORDER`).
**Consequence.** It is website purchases only (in-app and TikTok Shop values have other metric names, not fetched yet). Attribution follows each ad group's settings in TikTok, as in Ads Manager; GLIO cannot change it. Days synced before this change need a re-sync to show ROAS.

## ADR-032 Choose which ad accounts to connect

**Context.** TikTok's authorization grants every ad account the TikTok login can reach, and GLIO attached all of them to the client being connected. An agency login could pull other businesses' accounts into one client.
**Decision.** When TikTok authorises more than one ad account, nothing is attached: the token goes to Vault, and `pending_ad_connections` (migration 0015; server only: RLS on, no policies, no user grants) keeps the workspace, client, the user who started, the authorised accounts and the token's reference. The page `/integrations/tiktok/select/<id>` lists them (only for that user, only while they still manage the client): accounts already on this client are pre-ticked, accounts on another client are disabled, new ones are unticked. Confirming attaches only the chosen ids (ids TikTok did not authorise are refused), once; cancelling, choosing none, expiry (30 minutes, purged daily) and client deletion all delete the token when nothing uses it. One authorised account is attached directly, as before.
**Consequence.** TikTok still grants GLIO's token access to every authorised account; GLIO simply never stores or uses the ones not chosen. The page says how to remove that access in TikTok.

## ADR-033 Today so far: provisional, on demand, per campaign and per hour

**Context.** The dashboard stops at yesterday (complete days only). The owner wants to see today, per campaign and by hour.
**Decision.** Migration 0016 adds `metric_intraday` (grain `day` = the day so far per campaign, with purchase value; grain `hour` = per campaign per hour) and the sync-run kind `intraday`. The client page refreshes today when it is opened and the stored figures are older than 10 minutes (`refreshIntraday`: one fetch per account and day at a time, under an advisory lock; responses archived in `raw_platform_payloads` like every sync; the day's rows replaced as a whole), bounded to 8 s before showing what is stored; "Refresh" forces it (1-minute floor); the open page re-renders every 10 minutes. Yesterday's hours are fetched once after midnight for the comparison line. The Vercel Hobby plan's one daily cron rules out background polling; on-demand also keeps TikTok calls proportional to use. Purchase value and ROAS are day totals only: TikTok's purchase metrics are not available with `stat_time_hour` (doc 1751443967255553). Hours are in the ad account's time zone. Everything is labelled provisional and kept out of reports, emails, share links and reconciliation; completed days still come only from the daily sync. `purge_expired_data()` deletes intraday rows after 14 days, then the intraday runs' raw responses nothing else references (the raw archive's guard allows exactly that), then those runs.
**Consequence.** A busy day viewed often stores many small raw responses (identical ones are stored once); the 14-day purge bounds it. Today's figures change during the day and for days after (late attributions), as in Ads Manager.

## ADR-034 Disconnect a TikTok ad account from inside GLIO

**Context.** Owners could connect TikTok accounts but not disconnect them; revoking GLIO's access meant going to TikTok's settings.
**Decision.** "Disconnect" per account (owners/managers, client page). `disconnectAdAccount` sets the account to `disconnected`, deletes its credential row, expires its open change requests, and audits `ad_account.disconnected`. The token is revoked at TikTok (`POST /open_api/v1.3/oauth2/revoke_token/` with `app_id`, `secret`, `access_token`, verified against doc 1739965949088770) and deleted from Vault only when no other connected account uses the same token: one authorisation can cover several ad accounts (possibly on other clients), and revoking it would cut them all off. A failed revoke still disconnects and deletes GLIO's copy, and tells the owner how to remove the app in TikTok. History and reports are kept; connecting again reactivates the account.
**Consequence.** Owners control GLIO's access without leaving GLIO; deleting the data itself remains "delete client" (ADR-029).

## ADR-035 Break-even ROAS from the client's gross margin

**Context.** ROAS alone doesn't say whether ads make money: that depends on the client's margin.
**Decision.** Migration 0017 adds `client_economics` (one row per client: `gross_margin_pct`, 0 < m ≤ 100, two decimals; read by everyone who sees the client, edited by owners/managers, audited). Break-even ROAS = 100 / m. Comparisons are exact integer arithmetic (purchase value × m vs spend × 100%, in minor units) so a campaign exactly at break-even is never mislabelled by rounding. The dashboard's ROAS tile gets "Break-even X · above/below", campaign ROAS cells are marked ▲/▼ (words for screen readers, not colour alone), and a Profitability card shows margin, break-even, the period's ROAS and an estimated gross profit after ad spend (value × m − spend), labelled as an estimate based on TikTok-credited purchase value, excluding other costs.
**Consequence.** Not shown in reports, emails or share links yet (the margin is the agency's working figure, not necessarily something the client sees). With a Zid connection, the same margin will apply to real store sales.

## ADR-036 Every read of client data is audited, and owners can see it

**Context.** Only the client dashboard wrote `client.viewed`; report pages, figure source pages (raw platform data) and share links were reads without an audit entry, and nobody could read the log without SQL.
**Decision.** The report page writes `report.viewed`, the figure source page `figure.viewed` (with the figure id), both under the user's own permissions; opening a share link writes `report.share_viewed` as a system entry (`actor_label` share-link) with the share id and client, never IP, device or anything identifying the visitor. A new Activity page (owners/managers; the audit log's RLS already limits reading to them) lists the log newest first with filters by client and kind, in Arabic and English; `lib/activity.ts` labels every action and a test scans the code so a new action without a label fails.
**Consequence.** The log grows with every page view; it stays append-only (firm rule 5), and its retention period is still a legal question (COMPLIANCE.md).

## ADR-037 Deleting a workspace, and a person deleting their own account

**Context.** Deleting a whole workspace or a user account was "on request by email"; PDPL gives people the right to have their data deleted.
**Decision.** Owners delete a workspace from the Team page (typed name): `deleteWorkspaceData` writes `workspace.deleted` (name and counts) to the audit log, deletes the workspace row so every table cascades in one transaction, then revokes the workspace's TikTok tokens (best effort) and deletes them from Vault (`dropUnusedTokens`, now also used by client deletion). Anyone deletes their own account from "Your account" (typed email): refused while they are the only owner of a workspace (so no workspace is left ownerless or deleted by surprise); otherwise their open invitations are cancelled, `member.account_deleted` is audited in each workspace, and the Supabase sign-in record is deleted through the Admin API with `SUPABASE_SECRET_KEY` (server only, used for nothing else). Migration 0018 drops the foreign keys from "who did it" columns (requested_by, created_by, sent_by, updated_by, …) to `auth.users`, like `audit_log.actor_user_id` already: history and append-only records are never rewritten and keep only a bare id that no longer leads to a person ("former member"); memberships, notification settings and pending connections still cascade.
**Consequence.** Client data inside workspaces is not deleted by a member leaving; it belongs to the workspace and is deleted with the client or the workspace.

## ADR-038 Which sales count as purchase value: website, in-app, TikTok Shop (per client)

**Context.** ADR-031 fetched only website purchases (`total_complete_payment_rate`). Clients that sell in an app or on TikTok Shop had their ROAS understated.
**Decision.** Each client chooses, on the Profitability card, which sources count: website (pixel), in-app (`total_purchase_value`, ROAS `total_active_pay_roas`) and TikTok Shop gross revenue (`total_onsite_shopping_value`); at least one, default website (`client_economics.value_sources`, migration 0019, which also makes the margin optional so the choice can be saved without one). The sync requests only the chosen metrics and stores each in its own column (`purchase_value_minor`, `app_purchase_value_minor`, `shop_revenue_minor`), so nothing is double counted and every amount still traces to its raw payload. Reports, the dashboard and the Today view show their sum as "Purchase value" and ROAS = sum ÷ spend; the label names the sources when they are not just the website. If any chosen source is missing for a day the total is "missing for some days" rather than a smaller number. Reconciliation checks each source separately against TikTok's account totals. Changing the choice is audited (`client.value_sources_updated`) and applies from the next sync; resync a period to fill it in.
**Consequence.** Purchase metrics have no hourly data, so the Today view's value comes from the day-grain request. If a client attributes the same sale in two places (e.g. app and website), choosing both would double count: the hint tells owners to choose only where the client actually sells.

## ADR-039 Store sales from Zid: read-only, per store day, no customer data

**Context.** Ad platforms report the sales they attribute to themselves. WAKE UP sells on Zid; the owner wants real store sales beside them, an overall ROAS independent of attribution, and a check that TikTok tracking is plausible. Verified against docs.zid.sa (2026-11-27): OAuth code grant (no PKCE, `state` echoed), token response `authorization` + `access_token` (X-Manager-Token) + `refresh_token`; access tokens 3 years, refresh token 1 year (refresh on a schedule, a refresh revokes the old set); order list `GET /v1/managers/store/orders` with `date_from`/`date_to` carrying a UTC offset and `date_attribute=created_at`, 100 per page; `created_at` in responses has no time zone; 60 requests/minute per app per store.
**Decision.** One Zid store per client (migration 0020), connected by an owner/manager through Zid's permission page; the token set lives in Vault (`vault:glio/zid/…`) and is refreshed when older than 30 days, from the daily job. Because order times carry no zone, GLIO requests one store day at a time with the store's offset (Asia/Riyadh +0300), so day boundaries are explicit, never guessed. Each order is reduced in the connector to id, created time, status, payment status, total, currency and source; customer data never leaves the connector. Per day: cancelled (status canceled/cancelled or payment voided) left out; every other order counts at its order total (incl. VAT and shipping), paid or not (cash on delivery); full refunds (payment refunded or status reversed) deducted on the order's day; partial refunds counted and flagged, not deducted (the list gives no amount). The redacted day is archived immutably (deduplicated by content) and every `store_sales_daily` row points at it. The daily job re-syncs the last 7 days to pick up later cancellations and refunds. The client page shows orders, net sales, overall ROAS = net sales ÷ TikTok spend on the days that have store figures, and the tracking check (TikTok website purchase value vs store gross: above 105% = likely double counting; under 1% with 20+ orders and ad spend = pixel likely missing). Mixed currencies, missing totals and excess precision are errors, never converted or rounded.
**Consequence.** Not yet run against a real store: the first connection must be compared with Zid's own dashboard for a few days (RUNBOOK). Uninstall webhooks are not used (they carry no signature); a revoked install shows up as a refused sign-in, marks the store "needs reconnecting" and stops syncing. Salla can follow the same design.
